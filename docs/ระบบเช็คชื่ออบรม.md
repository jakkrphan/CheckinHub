# Prompt: ระบบลงทะเบียน + เช็คชื่อเข้าร่วมอบรม

สร้างเว็บแอประบบลงทะเบียน + เช็คชื่อเข้าร่วมอบรม โดยมี 3 ส่วนหลัก:

## 1) ORGANIZER PORTAL (ต้อง login)

- แสดงรายการโครงการเฉพาะที่ user คนนั้นเกี่ยวข้องเท่านั้น คือ:
  - (a) เป็นเจ้าของโครงการ (owner) หรือ
  - (b) ถูกเพิ่มชื่อเป็นผู้ร่วมจัด (collaborator) ในโครงการนั้น

  ห้ามดึงโครงการทั้งหมดในระบบมาแสดง ต้อง filter ที่ query ฝั่ง backend เสมอ
- **บทบาท `admin` (สิทธิ์ระดับระบบ แยกจาก owner/collaborator ของแต่ละโครงการ)**: ผู้ใช้ที่ `User.role = "admin"` เห็น**ทุกโครงการในระบบ**ได้โดยไม่ต้องเป็น owner หรือถูกเพิ่มเป็น collaborator (ข้อยกเว้นเดียวของกฎ filter ด้านบน) และจัดการบัญชีผู้ใช้อื่นได้ (เปลี่ยน role, ปิดการใช้งานบัญชี) แต่**ยังต้องผ่าน audit/log ทุกครั้งที่เข้าไปแก้ไขโครงการที่ตัวเองไม่ได้เป็น owner** เพื่อให้ตรวจสอบย้อนหลังได้ว่า admin เข้าไปทำอะไรในโครงการของคนอื่นบ้าง — สิทธิ์นี้มีไว้สำหรับดูแลระบบ/แก้ปัญหาเท่านั้น ไม่ใช่สิทธิ์ที่มอบให้ผู้จัดทั่วไป
- สร้าง/แก้ไข/ลบโครงการอบรม (ชื่อ, รายละเอียด, สถานที่, **วันปิดรับลงทะเบียน**, **โหมดอนุมัติ**, **ประเภทโครงการ**, **วันที่จัดอบรม**, **รูปปกโครงการ**)
  - ลบโครงการได้เฉพาะ owner เท่านั้น
- **สถานะโครงการ**: `draft` (ฉบับร่าง ยังไม่เปิดให้ลงทะเบียน กำลังตั้งฟิลด์/รอบ) → `published` (เปิดลิงก์ลงทะเบียนแล้ว) → `closed` (ปิดรับ/จบงานแล้ว)
  - สร้างโครงการใหม่เริ่มเป็น `draft` เสมอ ให้ผู้จัดตั้งฟิลด์ฟอร์ม/วัน/รอบให้ครบ แล้วกดปุ่ม "เผยแพร่" เองเมื่อพร้อม — หน้า public registration page จะขึ้น "ยังไม่เปิดรับลงทะเบียน" ถ้าโครงการยังเป็น draft แม้จะรู้ลิงก์ตรง ๆ
  - เปลี่ยนเป็น `closed` ได้เอง (ไม่ต้องรอ deadline) เช่นกรณีที่นั่งเต็มก่อนกำหนดหรือยกเลิกงาน
- **Clone โครงการ**: คัดลอกโครงการเดิม (ฟิลด์ฟอร์ม, ประเภท, โหมดอนุมัติ, รอบเช็คชื่อ) มาเป็นโครงการใหม่สถานะ `draft` ได้ทันที เหลือแค่แก้วันที่จัด/ที่นั่ง — ใช้บ่อยเวลาจัดอบรมรุ่นถัดไปที่ฟอร์ม/รูปแบบเดิมเกือบทั้งหมด
- **รูปปกโครงการ (cover image)**: อัปโหลดรูปปกได้ 1 รูปต่อโครงการ แสดงบนหน้ารายการโครงการฝั่ง organizer และบนสุดของหน้า public registration page ของโครงการนั้น
  - อัปโหลดผ่าน organizer portal ตอนสร้าง/แก้ไขโครงการ, เปลี่ยนรูปหรือลบรูปทีหลังได้ (ไม่บังคับต้องมี)
  - จำกัดชนิดไฟล์ `jpg/jpeg/png/webp` และขนาดไฟล์สูงสุด (เช่น 5MB) ตรวจสอบทั้งฝั่ง client (UX) และฝั่ง backend (บังคับจริง)
  - Resize/compress อัตโนมัติตอนอัปโหลดเพื่อลดขนาดไฟล์ก่อนเก็บ (เช่นผ่าน sharp) และตั้ง aspect ratio แนะนำ (เช่น 16:9) พร้อม crop preview ให้ผู้จัดเลือกก่อนบันทึก
  - เก็บไฟล์จริงไว้ที่ object storage (เช่น S3-compatible/Cloudflare R2/Vercel Blob) ไม่เก็บเป็น base64 ในฐานข้อมูล — ในตาราง `Event` เก็บแค่ URL
- **ประเภทโครงการ**: เลือกได้ 1 ค่าต่อโครงการ
  - **ภายใน (internal)** — ผู้เข้าร่วมเป็นบุคลากร/นักศึกษาภายในหน่วยงาน
  - **ภายนอก (external)** — เปิดรับบุคคลทั่วไปจากภายนอก
  - **ผสม (mixed)** — รับทั้งภายในและภายนอกในโครงการเดียวกัน
- **วันที่จัดอบรม (หลายวันได้ ไม่จำเป็นต้องต่อเนื่อง)**: ผู้จัดเพิ่ม/ลบ "วัน" ของโครงการเองได้ทีละแถว แต่ละแถวกำหนด
  - วันที่จัดจริง (เช่น จัดวันที่ 1, 5, 6 ของเดือน หรือจัดต่อเนื่องวันที่ 1, 2, 3)
  - **จำนวนที่นั่งรับของวันนั้น ๆ แยกกัน** (เช่น วันที่ 1 รับ 40 คน, วันที่ 5 รับ 60 คน) — แต่ละวันจำกัดจำนวนอิสระจากกัน ไม่ใช้ที่นั่งรวมเดียวกันทั้งโครงการ
  - อย่างน้อย 1 วันต่อโครงการ
- **โหมดอนุมัติผู้ลงทะเบียน**: มีติ๊ก/toggle ให้เลือกต่อโครงการว่า
  - **อนุมัติอัตโนมัติ (auto-approve)**: ระบบสร้าง QR + ส่งแจ้งเตือนทันทีที่ลงทะเบียนสำเร็จ ไม่ต้องรอผู้จัดกด
  - **อนุมัติเอง (manual, ค่าเริ่มต้น)**: เข้าสถานะ pending รอผู้จัด/ผู้ร่วมจัดกดอนุมัติ/ปฏิเสธตามเดิม
  - เปลี่ยนค่านี้ได้ตลอดระหว่างเปิดรับลงทะเบียน แต่มีผลกับผู้ที่ลงทะเบียน **หลังจากเปลี่ยนค่าเท่านั้น** — ผู้ที่ pending ค้างอยู่ก่อนหน้าไม่ถูกอนุมัติย้อนหลังอัตโนมัติ
- เจ้าของโครงการเพิ่ม/ลบผู้ร่วมจัดคนอื่นได้ (ค้นหาผู้ใช้จากอีเมลแล้วเพิ่มเข้าโครงการ) กำหนดระดับสิทธิ์ได้ 2 แบบต่อคน:
  - **เต็มสิทธิ์ (full)**: แก้ไขฟอร์ม/ดูแดชบอร์ด/อนุมัติผู้ลงทะเบียน/export/เช็คชื่อ ได้เหมือน owner แต่จัดการสิทธิ์คนอื่นหรือลบโครงการไม่ได้
  - **เช็คชื่ออย่างเดียว (check-in only)**: เข้าได้แค่ Check-in App ของโครงการนั้น ไม่เห็นคำตอบฟอร์ม/ข้อมูลส่วนตัวผู้ลงทะเบียนในหน้าอื่น — เหมาะกับเจ้าหน้าที่หน้างานที่ไม่ควรเห็นข้อมูลทั้งหมด
- **ป้องกันลงทะเบียนซ้ำ**: เช็คอีเมลซ้ำในโครงการเดียวกันตอนบันทึก (กันคนกดส่งฟอร์มซ้ำหลายรอบโดยไม่ตั้งใจ) ถ้าซ้ำแจ้งเตือนพร้อมลิงก์ไปหน้าเช็คสถานะของตัวเอง แทนที่จะสร้างแถวใหม่ซ้ำ
- **Dynamic Form Builder**: เพิ่ม/ลบ/เรียงลำดับฟิลด์ลงทะเบียนได้เอง
  - ชนิดฟิลด์ที่ต้องรองรับ: `text`, `textarea`, `email`, `tel`, `date`, `select` (dropdown), `checkbox` (เลือกได้หลายข้อ), `file` (แนบไฟล์ เช่น หนังสือคำสั่งไปราชการ/สำเนาบัตร)
    - `file`: จำกัดชนิดไฟล์ได้ต่อฟิลด์ (เช่น `pdf/jpg/png`) และขนาดสูงสุด (เช่น 5MB) เก็บไฟล์จริงที่ object storage เดียวกับรูปปกโครงการ — ใน `answers` JSON เก็บแค่ URL/path ของไฟล์ที่อัปโหลดแล้ว ไม่เก็บไฟล์ตรง ๆ ใน JSON
    - ต้อง validate ชนิด/ขนาดไฟล์ซ้ำที่ backend เสมอ (หน้านี้ไม่ login ปลอม request ได้ง่าย เหมือนฟิลด์อื่น)
  - แต่ละฟิลด์กำหนด `label`, `required` (บังคับ/ไม่บังคับ), `options` (สำหรับ select/checkbox)
  - เก็บนิยามฟิลด์เป็น JSON schema ผูกกับแต่ละโครงการ ไม่ hardcode fields ในโค้ด
  - **ฟิลด์แบบมีเงื่อนไข (conditional fields)**: ฟิลด์ใดก็ได้ตั้งให้ "แสดงเมื่อ" ฟิลด์แม่ (ต้องเป็น `select`/`checkbox` เท่านั้น) ถูกเลือกค่าตรงตามที่กำหนดได้ เช่น เลือก "ประเภทผู้เข้าร่วม = ข้าราชการ" แล้วค่อยโชว์ฟิลด์เพิ่ม "หน่วยงานต้นสังกัด", "ตำแหน่ง", "เลขที่คำสั่งไปราชการ"
    - ตั้งค่าใน builder: toggle "แสดงแบบมีเงื่อนไข" → เลือกฟิลด์แม่ (เฉพาะฟิลด์ type select/checkbox ที่สร้างมาก่อนหน้าฟิลด์นี้) → เลือกค่า (เลือกได้หลายค่า) ที่ทำให้ฟิลด์นี้โผล่
    - เก็บเป็น `conditional: { field, operator: "equals" | "in" | "includes", value }` ต่อฟิลด์ใน JSON schema
    - ฟิลด์ที่ยังไม่โชว์ (เงื่อนไขไม่ตรง) ไม่ถูกบังคับ required แม้ตั้ง required ไว้
    - ลบ/แก้ไขฟิลด์แม่ที่มีฟิลด์ลูกผูกอยู่ → ต้องเตือนผู้จัดก่อนว่ากระทบฟิลด์ลูก
- **กำหนดรอบเช็คชื่อ (Session)** ของโครงการเอง เช่น "เช้า", "บ่าย", "วันที่ 1" — เพิ่ม/ลบ/แก้ชื่อรอบได้อิสระ อย่างน้อย 1 รอบต่อโครงการ (สำหรับโครงการหลายวัน ผูกแต่ละรอบกับวันที่จัดวันใดวันหนึ่งได้ เช่น "วันที่ 1 - เช้า", "วันที่ 1 - บ่าย", "วันที่ 5 - เต็มวัน")
- **หน้ารายชื่อรออนุมัติ**: แสดงคำตอบของผู้ลงทะเบียนแต่ละคนตามฟิลด์ที่กำหนด พร้อมปุ่ม **อนุมัติ / ปฏิเสธ** เป็นรายคน (และเลือกอนุมัติหลายคนพร้อมกันได้)
  - กดอนุมัติ → ระบบสร้างรหัสลงทะเบียน + QR code แล้วส่งอีเมลตั๋วให้ผู้ลงทะเบียนทันที
  - กดปฏิเสธ → จบ ไม่ได้เข้าร่วม ไม่ได้รับ QR
  - **ค้นหา/กรองรายชื่อ**: ค้นหาด้วยชื่อ/อีเมล, กรองตามสถานะ, กรองตามวันที่เลือกเข้าร่วม, กรองตามคำตอบของฟิลด์ใดฟิลด์หนึ่ง (เช่น ดูเฉพาะกลุ่ม "ข้าราชการ") — จำเป็นมากเมื่อมีผู้ลงทะเบียนหลักร้อย/พันคน
- **เพิ่มผู้ลงทะเบียนเองโดยผู้จัด (manual add)**: สำหรับกรณีมีคนแจ้งชื่อทางโทรศัพท์/walk-in ไม่ได้กรอกผ่านฟอร์มสาธารณะ — กรอกข้อมูลตามฟิลด์เดียวกันแล้วเลือกให้สถานะ approved ได้ทันที (ได้ QR เลย)
- **ส่ง QR/แจ้งเตือนซ้ำ (resend)**: สำหรับคนที่ approved แล้วแต่อีเมลหาย/หา LINE ไม่เจอ มีปุ่ม "ส่งซ้ำ" ในหน้ารายชื่อ ส่งไปตามช่องทางที่เลือกไว้เดิม
- **ยกเลิก/ถอนการอนุมัติ (revoke)**: คนที่ approved แล้วแต่แจ้งไม่มาทีหลัง ผู้จัดกด "ยกเลิก" เปลี่ยนสถานะเป็น `cancelled` คืนที่นั่งให้คนอื่น (QR เดิมใช้เช็คชื่อไม่ได้อีก)
- **Waitlist**: ถ้าที่นั่งของวันที่เลือกเต็มแล้วตอนบันทึก (ทั้ง auto-approve และ manual mode) ให้สถานะเป็น `waitlisted` แทนที่จะปฏิเสธ — เมื่อมีคนถูก revoke/ยกเลิกเอง คิวถัดไปใน waitlist เลื่อนขึ้นแทนอัตโนมัติ (หรือแจ้งผู้จัดให้กดอนุมัติเองก็ได้แล้วแต่โหมด)
- **แจ้งเตือนแบบ broadcast**: ส่งข้อความประกาศถึงผู้ลงทะเบียนที่ approved ทั้งหมด (หรือเฉพาะบางวัน) พร้อมกันทางอีเมล/LINE เช่น แจ้งเลื่อนเวลา/เปลี่ยนสถานที่
- แดชบอร์ด: จำนวนรออนุมัติ / อนุมัติแล้ว / ปฏิเสธ / รอคิว (waitlisted) / ยกเลิก และยอดเช็คชื่อ **แยกตามแต่ละรอบ** (เช่น รอบเช้า 42/60, รอบบ่าย 38/60) แบบ polling refresh ทุก 3-5 วิ
- Export รายชื่อเป็น CSV (รวมสถานะอนุมัติและสถานะเช็คชื่อแต่ละรอบ)

## 2) PUBLIC REGISTRATION PAGE (ไม่ต้อง login)

- เปิดผ่านลิงก์เฉพาะของแต่ละโครงการ (เข้าไม่ได้ถ้าโครงการยังเป็นสถานะ `draft`)
- แสดง**รูปปกโครงการ** (ถ้ามี) ไว้บนสุดของหน้า ก่อนรายละเอียดโครงการและฟอร์ม — ถ้าไม่มีรูปปกให้ไม่ต้องแสดงพื้นที่ว่างเปล่า
- **ป้องกันบอท/สแปม**: ติด CAPTCHA (เช่น Cloudflare Turnstile) ก่อน submit + rate-limit จำนวนครั้งที่ submit ได้ต่อ IP ในช่วงเวลาหนึ่ง เพราะหน้านี้ไม่ login เป็นจุดเสี่ยงที่สุดในระบบ
- **PDPA consent**: มี checkbox ยินยอมให้เก็บ/ใช้ข้อมูลส่วนบุคคลตาม พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล บังคับติ๊กก่อน submit ได้ (โดยเฉพาะโครงการที่มีฟิลด์อ่อนไหวอย่างเลขคำสั่งราชการ)
- Render ฟอร์มแบบ dynamic ตาม schema ที่ผู้จัดกำหนดไว้ พร้อม validation ตาม required
  - **ฟิลด์แบบมีเงื่อนไข**: ซ่อนไว้ก่อน โผล่มาแบบ real-time เมื่อค่าฟิลด์แม่ตรงตามเงื่อนไข (เช่น เลือก "ข้าราชการ" แล้วฟิลด์หน่วยงานต้นสังกัดค่อยโผล่) — ฟิลด์ที่ยังซ่อนอยู่ไม่ต้อง validate required ฝั่ง client
  - **ต้อง validate เงื่อนไขซ้ำที่ backend เสมอ**: เช็คค่าฟิลด์แม่ที่ส่งมาจริงว่าตรงเงื่อนไขไหม ตรงก็บังคับ required ตามกำหนด ไม่ตรงก็เคลียร์ค่าฟิลด์ลูกทิ้งแม้ client จะแอบส่งมาด้วย (กันข้อมูลขยะปนใน `answers` JSON เพราะหน้านี้ไม่ login ปลอมข้อมูลได้ง่าย)
- **แสดงวันที่จัดอบรมของโครงการทั้งหมด พร้อมจำนวนที่นั่งคงเหลือของแต่ละวัน** (เช่น "วันที่ 1 — เหลือ 12/40 ที่", "วันที่ 5 — เต็มแล้ว", "วันที่ 6 — เหลือ 55/60 ที่")
  - ผู้ลงทะเบียน **เลือกวันที่จะเข้าร่วมได้หลายวันพร้อมกันในการลงทะเบียนครั้งเดียว** (เช่น ติ๊กเลือกทั้งวันที่ 1 และวันที่ 6) ไม่บังคับเลือกแค่วันเดียว
  - วันที่ที่นั่งเต็มแล้วให้ปิดไม่ให้เลือก (disable checkbox) แสดงสถานะ "เต็มแล้ว" ชัดเจน
  - ต้องเลือกอย่างน้อย 1 วัน ถึงจะ submit ฟอร์มได้
- **ปิดรับลงทะเบียนอัตโนมัติ** เมื่อเลย `registrationDeadline` ของโครงการนั้น — แสดงข้อความแจ้งว่าปิดรับแล้วแทนฟอร์ม
- **ช่องทางรับการแจ้งเตือน**: ให้ผู้ลงทะเบียนเลือกได้ว่าจะรับผลอนุมัติ/QR ทาง **อีเมล** หรือทาง **LINE Login** (สำหรับคนที่ไม่มีอีเมลหรือไม่สะดวกเช็คอีเมล) — ถ้าเลือก LINE ให้กดปุ่ม "เข้าสู่ระบบด้วย LINE" เพื่อเชื่อมบัญชี LINE ของตัวเองกับการลงทะเบียนนี้แทนการกรอกอีเมล (หรือกรอกทั้งสองอย่างก็ได้)
- หลังส่งฟอร์ม เช็ค `event.autoApprove` ของโครงการนั้น:
  - **autoApprove = false (ค่าเริ่มต้น)**: ต้องเช็คที่นั่งคงเหลือ **ของแต่ละวันที่เลือก** ณ ตอน submit เช่นกัน (ไม่ใช่เช็คแค่ตอนอนุมัติ) กันคนกรอกฟอร์มค้างไว้นานจนที่นั่งเต็มไปแล้ว — ถ้าเต็มให้เข้าสถานะ `waitlisted` แทน บันทึกข้อมูล สถานะเริ่มต้นเป็น **"รอการอนุมัติ" (pending)** — **ยังไม่สร้าง QR และยังไม่ส่งการแจ้งเตือนตั๋ว** แสดงข้อความ "ลงทะเบียนสำเร็จ กรุณารอการอนุมัติจากผู้จัด" แทน รอผู้จัดกดอนุมัติ/ปฏิเสธก่อนจึงจะสร้าง QR
  - **autoApprove = true**: ระบบตั้งสถานะเป็น **"approved" ทันที** สร้างรหัสลงทะเบียนเฉพาะบุคคล (unique code) + QR code และส่งแจ้งเตือนพร้อม QR ให้ทันทีตามช่องทางที่เลือก (อีเมล และ/หรือ LINE) โดยไม่ผ่านสถานะ pending — แสดงข้อความ "ลงทะเบียนสำเร็จ กรุณาตรวจสอบ QR code ที่ส่งให้"
    - ต้องเช็คจำนวนที่นั่งคงเหลือ **ของแต่ละวันที่เลือก** ณ ตอนบันทึก (กัน race condition คนสมัครพร้อมกันเกินที่นั่งของวันนั้น) — ถ้าวันใดวันหนึ่งที่เลือกเต็มแล้ว ให้เข้าสถานะ `waitlisted` แทนที่จะ auto-approve เกินจำนวนที่นั่งของวันนั้น
- ทั้งสองกรณี รหัสลงทะเบียน + QR ที่สร้างขึ้น (ไม่ว่าจะผ่าน manual approve หรือ auto-approve) ใช้ encode รหัสเดียวกันและใช้เช็คชื่อได้เหมือนกันทุกรอบของงาน — **รหัสต้องสุ่มแบบเดาไม่ได้** (UUID v4 หรือ crypto random ≥32 bytes) ห้ามออกเป็นเลขรันตามลำดับหรือรูปแบบที่เดาง่าย เพราะถ้าเดาถูกจะปลอม QR เข้างานได้โดยไม่ผ่านการอนุมัติจริง
- **หน้าเช็คสถานะ/ดู QR ของฉัน (self-service)**: ลิงก์แยกต่างหาก (ไม่ login เหมือนกัน) ให้ผู้ลงทะเบียนกรอกอีเมลหรือรหัสอ้างอิงที่ได้ตอน submit เพื่อกลับมาดูสถานะล่าสุด (pending/approved/waitlisted/rejected) และดู/ดาวน์โหลด QR ซ้ำได้เองโดยไม่ต้องรอผู้จัด resend ให้
  - จากหน้าเดียวกันนี้ ผู้ลงทะเบียนกด **"ยกเลิกการเข้าร่วม" เองได้ (self-cancel)** ถ้ามาไม่ได้ — คืนที่นั่งให้คนถัดไปใน waitlist ทันที

## 3) CHECK-IN APP (สำหรับเจ้าหน้าที่หน้างาน, ต้อง login)

- เลือกโครงการที่จะเช็คชื่อ (เห็นเฉพาะโครงการที่ตัวเองมีสิทธิ์ตามกติกาข้อ 1)
- **เลือกรอบเช็คชื่อ (session)** ก่อนเริ่มสแกน/ยิง/ค้นหา (เช่น เลือก "รอบเช้า") — เปลี่ยนรอบได้ตลอดจากหน้าเดียวกัน
- รองรับ 3 วิธีเช็คชื่อ:
  - **a. สแกนผ่านกล้องมือถือ/เว็บแคม** — ใช้ jsQR หรือ ZXing decode จาก video stream
  - **b. เครื่องยิงบาร์โค้ด/QR แบบ USB หรือ Bluetooth** — ทำงานเป็น keyboard-wedge คือพิมพ์รหัสแล้วส่ง Enter ให้เอง ต้องมี input ที่ auto-focus ตลอดเวลาและ listen `keydown` Enter เพื่อ trigger เช็คชื่อทันที
  - **c. ค้นหาชื่อ/รหัสด้วยมือ** แล้วกดปุ่มเช็คชื่อ
- เช็คชื่อได้เฉพาะผู้ลงทะเบียนที่สถานะ **approved** เท่านั้น (คน pending, waitlisted หรือ rejected เช็คชื่อไม่ได้ ต้องแจ้งเตือนชัดเจนถ้าพยายามสแกน)
- **⚠️ ต้องเช็คว่าคนที่สแกนเลือก "วันนี้" ไว้จริงหรือไม่**: เนื่องจากผู้ลงทะเบียนเลือกเข้าร่วมได้หลายวัน ถ้า session ที่กำลังเช็คอยู่ผูกกับ `eventDayId` ใดวันหนึ่ง ต้องตรวจสอบว่า registrant คนนั้นมีแถวใน `RegistrantEventDay` ของวันนั้นจริงก่อนให้เช็คชื่อผ่าน — ถ้าไม่ตรง (เช่น ลงทะเบียนไว้แค่วันที่ 1 แต่มาสแกนวันที่ 6) ต้องเตือนเจ้าหน้าที่ชัดเจนว่า "ไม่ได้ลงทะเบียนวันนี้ไว้" แม้สถานะจะ approved ก็ตาม ไม่ใช่ปล่อยผ่านอัตโนมัติ
- **กันสแกนซ้ำเฉพาะภายในรอบเดียวกัน**: คนเดิมสแกนซ้ำในรอบที่เลือกอยู่ → แจ้งเตือน "เช็คชื่อรอบนี้ไปแล้ว" ไม่ error; แต่คนเดิมเช็คชื่อในคนละรอบ (เช่น เช้ากับบ่าย) ต้องทำได้ตามปกติ เพราะนับแยกกัน
- **Feedback หลังสแกนต้องชัดและเร็ว**: แสดงชื่อ + ข้อมูลสำคัญของผู้ลงทะเบียนบนจอทันทีหลังสแกนสำเร็จ พร้อมสี/เสียง beep แยกกรณีชัดเจน — เขียว = เช็คชื่อสำเร็จ, เหลือง = เช็คซ้ำ/ไม่ตรงวัน, แดง = ไม่พบ/ยังไม่ approved (จำเป็นเพราะเจ้าหน้าที่หน้างานมักไม่ได้จ้องจอตลอดเวลา)
- **Undo การเช็คชื่อผิดคน**: กดเช็คชื่อผิดคนโดยไม่ตั้งใจ (พบบ่อยเวลาคนแน่น) ต้องมีปุ่ม "ยกเลิก" ลบ record เช็คชื่อล่าสุดได้ทันทีจากหน้าเดียวกัน
- **ค้นหาด้วยมือรองรับกรณีแก้ไขข้อมูลเล็กน้อยก่อนเช็คชื่อได้** (เช่น กรอกชื่อผิดตอนลงทะเบียน, สแกนไม่ติดเพราะมือถือแบตหมด) ไม่ใช่แค่ค้นแล้วกดเช็คอย่างเดียว
- อัปเดตสถานะเช็คชื่อของแต่ละรอบให้ทุกอุปกรณ์ที่เปิดหน้านี้อยู่เห็นตรงกัน ผ่านการ poll ข้อมูลใหม่ทุก 3-5 วินาที (กันกรณีมีหลายจุดเช็คชื่อพร้อมกัน)
- **Resilience ตอนเน็ตหลุดหน้างาน**: ถ้า request เช็คชื่อส่งไม่สำเร็จ ต้อง queue ไว้ใน local (เช่น localStorage/IndexedDB) แล้ว sync อัตโนมัติเมื่อเน็ตกลับมา พร้อมแจ้งเตือนสถานะ "ยังไม่บันทึก รอ sync" ชัดเจน ห้ามทำเหมือนเช็คผ่านแล้วแต่ข้อมูลหายจริง

model User {
  id          String   @id @default(cuid())
  name        String
  email       String   @unique
  role        String   @default("organizer") // organizer | staff | admin
  ownedEvents Event[]          @relation("EventOwner")

model Event {
  id                   String   @id @default(cuid())
  title                String
  description          String?  @db.Text
  location             String?
  eventType            String   @default("internal") // internal | external | mixed
  status               String   @default("draft") // draft | published | closed
  coverImageUrl        String?  // URL รูปปกโครงการ เก็บไฟล์จริงไว้ที่ object storage
  fields               Json     // [{key, label, type, options[], required, conditional?}]
  registrationDeadline DateTime? // ปิดรับลงทะเบียนอัตโนมัติหลังเวลานี้
  autoApprove          Boolean  @default(false) // true = อนุมัติผู้ลงทะเบียนอัตโนมัติทันที, false = ต้องรอผู้จัดอนุมัติเอง
  createdAt            DateTime @default(now())

  ownerId     String
  owner       User             @relation("EventOwner", fields: [ownerId], references: [id])
  organizers  EventOrganizer[] // ผู้ร่วมจัด นอกเหนือจากเจ้าของ
  days        EventDay[]       // วันที่จัดอบรม (หลายวันได้ ไม่ต่อเนื่องก็ได้) แต่ละวันมีที่นั่งแยกกัน
  sessions    Session[]        // รอบเช็คชื่อของโครงการนี้ เช่น เช้า / บ่าย
  registrants Registrant[]
}

// วันที่จัดอบรมแต่ละวันของโครงการ (1 โครงการมีได้หลายวัน ไม่ต้องต่อเนื่อง)
model EventDay {
  id       String   @id @default(cuid())
  eventId  String
  event    Event    @relation(fields: [eventId], references: [id])
  date     DateTime // วันที่จัดจริงของวันนี้
  maxSeats Int?     // จำนวนที่นั่งรับของวันนี้โดยเฉพาะ (null = ไม่จำกัด)

  registrantDays RegistrantEventDay[] // ใครเลือกเข้าร่วมวันนี้บ้าง
  sessions       Session[]            // รอบเช็คชื่อที่ผูกกับวันนี้ (ถ้ามี)

  @@unique([eventId, date])
}

// ตารางกลาง: ใครมีสิทธิ์เห็น/จัดการโครงการไหนบ้าง
model EventOrganizer {
  id      String   @id @default(cuid())
  eventId String
  event   Event    @relation(fields: [eventId], references: [id])
  userId  String
  user    User     @relation(fields: [userId], references: [id])
  role    String   @default("full") // full | checkin_only
  addedAt DateTime @default(now())

  @@unique([eventId, userId]) // 1 คนถูกเพิ่มซ้ำในโครงการเดียวกันไม่ได้
}

// รอบเช็คชื่อของแต่ละโครงการ (ผู้จัดกำหนดเอง อย่างน้อย 1 รอบ)
model Session {
  id         String   @id @default(cuid())
  eventId    String
  event      Event    @relation(fields: [eventId], references: [id])
  eventDayId String?  // ผูกกับวันจัดวันใดวันหนึ่ง (ไม่บังคับ) เผื่อโครงการหลายวันอยากแยกรอบตามวัน
  eventDay   EventDay? @relation(fields: [eventDayId], references: [id])
  label      String   // เช่น "เช้า", "บ่าย", "วันที่ 1 - เต็มวัน"
  startTime  DateTime?
  endTime    DateTime?
  checkIns   CheckIn[]
}

model Registrant {
  id           String    @id @default(cuid())
  eventId      String
  event        Event     @relation(fields: [eventId], references: [id])
  answers      Json      // {field_key: value}
  registeredAt DateTime  @default(now())

  email        String?   // อาจไม่มีถ้าเลือกรับแจ้งเตือนผ่าน LINE แทน
  lineUserId   String?   // ได้จาก LINE Login ตอนลงทะเบียน ใช้ push ข้อความแจ้งเตือน
  notifyVia    String    @default("email") // email | line | both

  status       String    @default("pending") // pending | approved | rejected | waitlisted | cancelled
  approvedAt   DateTime?
  approvedBy   String?   // userId ของผู้จัดที่กดอนุมัติ/ปฏิเสธ
  cancelledAt  DateTime? // เวลาที่ถูก revoke (โดยผู้จัด) หรือ self-cancel (โดยผู้ลงทะเบียนเอง)
  qrCode       String?   // สร้างเมื่อ approved เท่านั้น ตอน pending/waitlisted เป็น null, ถูกเคลียร์ทิ้งถ้า cancelled — ⚠️ ต้องเป็นค่าสุ่มที่เดาไม่ได้ (เช่น UUID v4 หรือ crypto random อย่างน้อย 32 bytes) ห้ามใช้เลขรันตามลำดับ/เดาง่าย เพราะเดาถูกแล้วปลอมเข้างานได้

  checkIns     CheckIn[] // เช็คชื่อได้หลายรอบ คนละ record
  days         RegistrantEventDay[] // วันที่เลือกเข้าร่วม (เลือกได้หลายวัน)

  @@index([eventId])
  @@unique([eventId, email]) // กันลงทะเบียนอีเมลซ้ำในโครงการเดียวกัน (MySQL ปล่อยผ่านได้ถ้า email เป็น null หลายแถว)
}

// ตารางกลาง: ผู้ลงทะเบียน 1 คน เลือกเข้าร่วมได้หลายวัน (many-to-many)
model RegistrantEventDay {

  registrantId String
  registrant   Registrant @relation(fields: [registrantId], references: [id])
  eventDayId   String
  eventDay     EventDay   @relation(fields: [eventDayId], references: [id])

  @@unique([registrantId, eventDayId]) // เลือกวันเดียวกันซ้ำไม่ได้
}

// เช็คชื่อ 1 record ต่อ 1 คน ต่อ 1 รอบ
model CheckIn {

  checkedInAt  DateTime   @default(now())
  checkedInBy  String?

  @@unique([registrantId, sessionId]) // เช็คซ้ำในรอบเดียวกันไม่ได้ แต่คนละรอบเช็คได้อีก
}

## ACCESS CONTROL

ต้อง enforce ที่ backend/API ทุก endpoint ไม่ใช่แค่ซ่อนใน UI:

- รายการโครงการ, แก้ไขฟอร์ม, ดูแดชบอร์ด, อนุมัติ/ปฏิเสธผู้ลงทะเบียน, export CSV, เข้าหน้าเช็คชื่อ: ต้องเป็น owner หรือมีแถวใน `EventOrganizer` ของโครงการนั้นเท่านั้นถึงเข้าถึงได้
  - ถ้า `EventOrganizer.role = "checkin_only"` เข้าได้แค่ endpoint ของ Check-in App เท่านั้น endpoint อื่น (ฟอร์ม, คำตอบผู้ลงทะเบียน, dashboard, export) ต้อง reject แม้จะอยู่ในโครงการเดียวกัน
- ลบโครงการ / เพิ่ม-ลบผู้ร่วมจัด / เปลี่ยนสถานะโครงการ (publish/close): เฉพาะ owner เท่านั้น
- ต้องมี middleware/guard ตรวจสิทธิ์นี้ทุกครั้งที่ request เข้าถึงข้อมูลของ event ใด ๆ

## TECH STACK ที่ต้องการ

- **Frontend**: Next.js (App Router) + TypeScript + **shadcn/ui** (Radix UI primitives + Tailwind CSS ใต้ฮู้ด, ใช้ CLI ของ shadcn เพิ่มคอมโพเนนต์ทีละตัว เช่น form, table, dialog, badge)
- **Database**: MySQL 8 + Prisma ORM (เก็บ `fields` ของ event และ `answers` ของ registrant เป็น column ชนิด JSON เพื่อรองรับฟิลด์ที่แต่ละโครงการกำหนดเองได้โดยไม่ต้อง migrate schema)
- **Realtime**: polling ทุก 3-5 วินาทีบนหน้าแดชบอร์ด, หน้ารออนุมัติ, และหน้าเช็คชื่อ (ไม่ใช้ Socket.io เพื่อลดความซับซ้อน — ถ้าต้องการ real-time เป๊ะกว่านี้ค่อยอัปเกรดทีหลัง)
- **Auth (ฝั่ง organizer/staff)**: NextAuth.js (Credentials provider) แยกสิทธิ์ organizer / staff / admin
- **LINE Login (ฝั่งผู้ลงทะเบียน)**: LINE Login เพื่อรับ `lineUserId` ตอนลงทะเบียน และ **LINE Messaging API** สำหรับ push ข้อความแจ้งผลอนุมัติ + QR ให้คนที่ไม่มี/ไม่ใช้อีเมล
- **QR generation**: `qrcode` (npm) — สร้างตอนอนุมัติเท่านั้น โดย encode รหัสจาก `crypto.randomUUID()` หรือ `crypto.randomBytes(32)` (ห้ามใช้ ID ที่รันตามลำดับ)
- **QR scanning (กล้อง)**: `jsQR` หรือ `@zxing/browser`
- **Email**: Resend หรือ Nodemailer + SMTP สำหรับส่งอีเมลตั๋ว (ส่งหลังอนุมัติ ให้คนที่เลือกรับทางอีเมล)
- **Hosting**: Vercel หรือ VPS ธรรมดา (frontend) + PlanetScale / Railway / VPS ที่มี MySQL (backend)
- **Export CSV**: `papaparse`
- **Image upload/storage**: object storage สำหรับรูปปกโครงการและไฟล์แนบจากฟิลด์ `file` (S3-compatible / Cloudflare R2 / Vercel Blob) + `sharp` สำหรับ resize/compress รูปภาพก่อนเก็บ
- **Bot protection**: Cloudflare Turnstile (หรือ hCaptcha) บนหน้า public registration page

## ข้อกำหนดเพิ่มเติม

- Mobile-responsive ทุกหน้า โดยเฉพาะหน้าเช็คชื่อหน้างานที่ต้องใช้งานบนมือถือ/แท็บเล็ตได้ดี
- หน้าเช็คชื่อต้องรองรับทั้งอินพุตจากกล้องและจากเครื่องยิงบาร์โค้ดพร้อมกันในหน้าเดียว
- ระบบต้องรองรับหลายโครงการพร้อมกัน แต่ละโครงการมีฟิลด์ลงทะเบียนและรอบเช็คชื่อต่างกันได้อิสระ
- ป้องกัน SQL injection / validate input ทุกจุดที่รับข้อมูลจากผู้ใช้ภายนอก (หน้าลงทะเบียนสาธารณะเป็นจุดเสี่ยงที่สุด เพราะไม่ต้อง login)

## Flow การทำงานโดยสรุป

**ผู้จัด (ตั้งค่าก่อนเปิดลงทะเบียน):** สร้างโครงการ สถานะเริ่มเป็น `draft` (ระบุประเภทภายใน/ภายนอก/ผสม + วันปิดรับลงทะเบียน + เลือกโหมดอนุมัติ auto/manual) → เพิ่มวันที่จัดอบรม (วันเดียวหรือหลายวัน ไม่ต้องต่อเนื่อง) พร้อมกำหนดที่นั่งรับของแต่ละวัน → กำหนดฟิลด์ลงทะเบียน → กำหนดรอบเช็คชื่อ (เช้า/บ่าย ฯลฯ ผูกกับวันใดวันหนึ่งได้) → เพิ่มผู้ร่วมจัด (เต็มสิทธิ์ หรือเช็คชื่ออย่างเดียว) → กด **เผยแพร่ (publish)** เมื่อพร้อม

**ผู้เข้าอบรม (ลงทะเบียน):** เห็นรายการวันที่จัด + ที่นั่งคงเหลือของแต่ละวัน → เลือกวันที่จะเข้าร่วม (เลือกได้หลายวันพร้อมกัน) → กรอกฟอร์ม เลือกช่องทางรับแจ้งเตือน (อีเมล และ/หรือเข้าสู่ระบบด้วย LINE สำหรับคนไม่มีอีเมล) → ติ๊กยินยอม PDPA → submit (ผ่าน CAPTCHA, ปิดอัตโนมัติเมื่อเลย deadline) →
  - ที่นั่งของวันที่เลือกยังพอ + โครงการเป็น **manual (ค่าเริ่มต้น)** → สถานะ `pending` ยังไม่ได้รับ QR รอผู้จัดอนุมัติ
  - ที่นั่งของวันที่เลือกยังพอ + โครงการเป็น **auto-approve** → สถานะ `approved` ทันที ได้รับ QR + แจ้งเตือนทันที ข้ามขั้นตอนรออนุมัติ
  - ที่นั่งของวันที่เลือกเต็มแล้ว (ทั้งสองโหมด) → สถานะ `waitlisted` รอคิว
  - ผู้ลงทะเบียนกลับมาเช็คสถานะ/ดู QR ซ้ำ หรือยกเลิกเอง (self-cancel) ได้ทุกเมื่อผ่านหน้าเช็คสถานะ

**ผู้จัด (อนุมัติ, เฉพาะโครงการโหมด manual):** ตรวจคำตอบรายคน (ค้นหา/กรองได้) → อนุมัติ (สร้าง QR + ส่งแจ้งเตือนทันทีตามช่องทางที่เลือก) หรือปฏิเสธ (จบ) — เพิ่มคนเข้าระบบเองแบบ manual ได้ถ้าจำเป็น, ส่ง QR ซ้ำได้, ยกเลิก/ถอนการอนุมัติ (revoke) คืนที่นั่งให้คิว waitlist ได้, ส่งประกาศ broadcast ถึงทุกคนที่ approved ได้

**ผู้เข้าอบรม:** ได้รับ QR ทางอีเมลหรือ LINE หลังอนุมัติ ใช้ QR เดียวกันเช็คชื่อได้ทุกรอบของงาน

**เจ้าหน้าที่หน้างาน (วันงานจริง):** เลือกโครงการ → เลือกรอบที่จะเช็ค → เช็คชื่อด้วยกล้อง/เครื่องยิง/ค้นหา (เฉพาะคนสถานะ `approved` **และ**เลือกวันนี้ไว้จริง) → เช็คซ้ำในรอบเดียวกันถูกกัน แต่คนละรอบเช็คได้อีก → เห็น feedback สี/เสียงชัดเจนทันที แก้ไข/undo ได้ถ้าพลาด → สถานะอัปเดตเรียลไทม์ทุกจุด แม้เน็ตหลุดก็ queue ไว้ sync ทีหลังได้

**ผู้จัด (ระหว่างงาน):** ดูแดชบอร์ดยอดรออนุมัติ/อนุมัติแล้ว/ปฏิเสธ/รอคิว/ยกเลิก และยอดเช็คชื่อแยกตามแต่ละรอบ

## ลำดับการพัฒนาที่แนะนำ

เริ่มจากด้านที่ "ของอื่นต้องพึ่งพา" ไปหาด้านที่ "พึ่งพาของอื่น" — แต่ละขั้นทดสอบจบเป็นระยะได้ ไม่ต้องรอจบทั้งระบบถึงจะเห็นผล

1. **Setup โปรเจกต์ + วาง Prisma schema ทั้งหมดให้จบก่อน** — Next.js (App Router) + TS + shadcn/ui, ต่อ MySQL, ตั้ง `.env` ใส่ทุก model ที่คุยกันไว้ทีเดียว เพราะ field/relation กระทบทุกหน้าที่จะสร้างทีหลัง แก้ทีหลังจะย้อนแก้เยอะกว่ามาก
2. **Auth (NextAuth Credentials) + access control guard** — เขียน guard function กลาง (เช็ค owner/collaborator/role `checkin_only`/`admin`) ใช้ซ้ำได้ทั้ง server component และ API route เพราะทุกหน้าใน Organizer Portal และ Check-in App ต้องพึ่งพาสิ่งนี้
3. **CRUD โครงการพื้นฐาน (ยังไม่ต้องมี form builder)** — สร้าง/แก้ไข/ลบโครงการ, สถานะ draft/published/closed, วันที่จัดอบรมหลายวัน, ประเภทโครงการ, รูปปก — ต้องมี event จริงในระบบก่อนถึงจะไปต่อขั้นถัดไปได้
4. **Dynamic Form Builder + Conditional Fields** — ต้องมี event จริงให้ผูก JSON schema ของฟิลด์เข้าไป รวมฟิลด์ `file` upload
5. **Public Registration Page** — ต้องมี form schema จริงถึงจะ render ฟอร์ม dynamic ได้ รวม CAPTCHA, PDPA consent, เลือกวันที่เข้าร่วมหลายวัน, เช็คที่นั่ง/waitlist
6. **หน้าอนุมัติ + แดชบอร์ด + แจ้งเตือน (Email/LINE) + Export CSV** — ต้องมี registrant จริงจากขั้นก่อนหน้ามาทดสอบ approve/reject/waitlist/revoke/resend/broadcast
7. **Check-in App (กล้อง/เครื่องยิง/ค้นหา)** — ทำเป็นลำดับสุดท้ายเพราะต้องมีคนสถานะ `approved` จริงมาทดสอบสแกน รวม logic เช็ควันที่ตรง, กันสแกนซ้ำ, undo, offline queue
